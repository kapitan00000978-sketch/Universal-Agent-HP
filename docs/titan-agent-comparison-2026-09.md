# TITAN agent comparison — September 2026

## Scope and method

This is a **capability and architecture comparison**, not a performance ranking. TITAN observations below come from a static review of this repository and the current test suite. Competitor observations are limited to features described in their official documentation. Products, deployment modes, and defaults can change; re-check documentation before using this as a procurement or security decision.

No same-model, same-task, same-environment head-to-head benchmark was run. Therefore this document makes **no claims** that TITAN is more capable, safer, faster, or more successful than another agent. A feature being present in a codebase also does not establish that it works reliably or is secure in every deployment.

## TITAN capability audit

### Implemented evidence in this repository

- A local `ToolRegistry` instance returns 103 base tool definitions at the time of this review. The catalog includes command and file operations, web search/scraping, browser/desktop-related actions, sandbox/Docker helpers, and other integrations. Tool count measures breadth only—not correctness, safety, or usefulness.
- Agent orchestration adds role-based tool filtering, memory/skill tools, Git operations, optional MCP tools, and opt-in dynamic tool synthesis.
- `analyze_python_file` and `analyze_python_repository` provide bounded AST summaries of source files, module definitions, and local import dependencies without importing or executing project code. They assist repository understanding but do not capture all dynamic behavior.
- Ordinary `execute_command`, `python_eval`, `sandbox_execute`, DeepCoder verification, and TDD test execution use the Docker sandbox by default. It disables network access, sets the container root filesystem read-only, drops Linux capabilities, disables privilege escalation, and applies CPU/memory/PID limits. The project workspace is the intended read/write mount for normal commands. Missing Docker fails closed; this runtime has no Docker daemon, so actual container behavior was **not** exercised here—only the generated invocation was mocked and inspected.
- File-tool paths are constrained to the resolved workspace (including symlink resolution) outside `TITAN_FULL_ACCESS`. Explicit `TITAN_FULL_ACCESS` remains a trusted-mode bypass: host command/code execution and relaxed approval gates may be enabled.
- Selected high-impact actions and all MCP tools require a live approval manager in normal mode; policy DENY now blocks rather than falling through. Dynamic tool synthesis remains opt-in and requires a live approval manager for creation and each invocation. Generated source is verified and invoked only through fresh Docker containers; no in-process import/load path remains. The actual container boundary remains unverified in this Docker-less environment.
- Policy and approval checks exist for selected actions. `TITAN_FULL_ACCESS` explicitly relaxes approval requirements; deployments must treat that as a deliberate trust-mode choice.
- Classic tool batches persist a `tool_in_progress` checkpoint before execution; structured runs persist their in-progress state before starting. If persistence fails, execution is blocked. Ambiguous work is never automatically replayed. An authenticated reconciliation endpoint now accepts an exact operator-verified outcome for every pending classic `tool_call_id`, records the operator and outcome, and allows the session to resume without re-running those calls. Structured runs still pause and need a fresh run; this is not exactly-once execution.
- The latest full local test suite passed **802 tests** on 2026-09-30 after the hardening changes. Sandbox tests inspect mocked Docker invocations and fail-closed behavior; they do not execute real containers or destructive external actions, certify isolation, or compare task success with other agents.

### Relative strengths (feature breadth, not superiority)

1. **Broad general-purpose surface:** TITAN combines coding and non-coding tools in one codebase, rather than presenting only a coding-agent workflow.
2. **Extensibility:** Python tool registry, skills, MCP hooks, role-aware tool definitions, and optional agent/tool extensions make it adaptable for custom workflows.
3. **Conservative checkpoint guard:** Before a batch of potentially side-effecting calls, TITAN records intent and refuses to start if it cannot persist it; uncertain interrupted work is not blindly replayed. Classic batches have an authenticated manual reconciliation path.

### Main gaps and risks to address

1. **Validate the container at runtime:** The sandbox default is implemented, but this workspace has no Docker daemon; run destructive-free smoke tests in a disposable CI VM, inspect actual mounts/network/resource limits, and test timeout cleanup before claiming operational isolation.
2. **Verify every code-execution route:** Dynamic tool synthesis now verifies and invokes generated tools through fresh Docker containers; no generated handler is imported into the agent process. This design is covered by mocked runner tests only, so validate real mounts, network isolation, cleanup, and resource limits in a disposable Docker CI environment. Audit other host-side subprocesses separately.
3. **Consistent approval boundary:** High-impact action families and MCP now fail closed without human approval, and DENY is enforced. Continue auditing new tools and delegated agents so additions cannot bypass classification; keep the explicit FULL_ACCESS bypass obvious and audited.
4. **Durable recovery completeness:** Classic tool batches can now be operator-reconciled. Structured engine state and approval-pending checkpoints are still not resumable; do not automatically replay uncertain side effects.
5. **Controlled evaluation:** A repeatable task set and scorer are in the repository, but no live cross-agent score exists. Compare with matched models, prompts, tool access, budgets, network and workspaces; report success, regressions, time, cost, errors, and safety incidents across repeated trials.
6. **Security/effectiveness validation:** Threat-model prompt injection, secrets in checkpoints, untrusted browser content, MCP servers, and generated tools. Unit tests are necessary but not security certification.

## Bottom line

TITAN is a broad, extensible agent codebase with default Docker isolation for its primary command/Python/testing paths, workspace path confinement, stronger centralized approvals, and explicit checkpoint reconciliation for classic tool batches. Generated tools are now verified and invoked only through Docker-backed runners rather than imported into the agent process. Important limits remain: Docker was not available for runtime validation in this environment; FULL_ACCESS deliberately bypasses protections; container escape resistance and derived-image behavior are unverified; and structured runs cannot yet be reconciled. No controlled comparison has established whether TITAN performs better or worse on real tasks.
